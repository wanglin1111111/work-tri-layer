# AI 教练闭环：四步循环与三件资产

> 核心：把每个任务都跑成「目标 → AI 拆步骤 → AI 执行 → 我按验收清单检查」。**用熟了这个循环 = 现成的「智能体开发」能力**——名单里"智能体开发员"的岗位定义就是这个循环的规模化版本。

## 一、四步闭环指令模板

### ① 目标（我写，不是 AI 写）

```
模板：
  目标：<要达成什么，一句话，含完成判据>
  约束：<时间/预算/不可动的部分>
  验收标准：
    - <标准1>（可客观判定）
    - <标准2>
    - <标准3>（3-5 条，从验收清单库取，没有现写）
关键纪律：验收标准我写（或我确认 AI 起草的初稿）。
  验收标准交给 AI 定 = 判断层外包 = 循环失效。
```

### ② AI 拆步骤（AI 出，我确认）

```
指令模板：
  "基于以下目标与验收标准，给出执行步骤。
   每步标注：产出物 + 预计耗时。
   步骤里凡涉及'判断/取舍'的，标出需要我确认的决策点。"
我的动作：确认或改。
  照单全收 = 把指挥权外包（决策点没经过我 = 这步等于我没指挥）。
```

### ③ AI 执行

```
指令模板（每步单独下，不要一次下完）：
  "执行步骤 N：<步骤内容>。
   只产出这一步的产出物，不要顺手做下一步。
   遇到步骤外的判断需求，停下来问我，不要自己拍板。"
关键纪律：分步下指令，产出物逐步验收——一次下完整条链 = 中间错了全链返工。
```

### ④ 我按验收清单检查

```
检查动作：
  逐条过验收清单（不是"看一遍觉得差不多"）：
    - 每条标 过/不过
    - 不过的 → 打回指令："第 __ 条不满足：<具体差在哪>，重做步骤 __"
打回机制：
  最多 2 轮打回。
  第 2 轮仍不过 = 停。原因只有两种：
    (a) 目标定错了 → 回步骤①重定目标
    (b) 验收标准不合理（太严/偏了）→ 改标准，但改标准必须记录
        （为什么改——这是判断层的数据，不是妥协）
  第 3 轮打回 = 成本失控，禁止（与 taste-gate 时间盒同构）。
```

## 二、验收清单写法（每类任务 3-5 条「怎样算做对」）

### 定清单的方法（从翻车里长出来）

```
第 1 版清单来源（三选一，按可得性）：
  a) 该类任务历史上返工的原因（每次返工 = 一条漏掉的验收标准）
  b) 下游使用者挑过的毛病（"这个初稿哪里不能用"= 验收标准）
  c) 交付物的客观属性（字数/格式/必含字段/数据来源——硬性可判定）
3-5 条的取舍：
  少于 3 条 = 判断标准没成型（AI 产出 60 分你也会收）
  多于 5 条 = 清单变审查流程（检查成本 > 返工成本，检查形同虚设）
每条的格式：
  <判定对象> <方向> <阈值/判据>
  例："数据来源" "全部可溯源" "每个数字带出处"
  例："初稿结构" "包含" "结论前置（第一段有结论）"
禁止的写法：
  "质量要好" / "专业一点" / "符合规范"（无判据 = 检查时全凭感觉 = 判断层没建成）
```

### 清单维护（月度盘点）

```
[ ] 这条清单这个月拦截了什么？（拦截 0 次 = 这条要么太松要么任务变了，审查）
[ ] 这个月新返工的原因，清单里有对应条款吗？（没有 = 补进去）
[ ] 翻车记录里重复 ≥3 次的错误，进清单了吗？（没进 = 翻车白翻了）
```

## 三、打回机制的边界（什么时候不是打回）

| 现象 | 是打回吗 | 处置 |
|---|---|---|
| 单条验收不过，其余过 | 是 | 打回重做该步骤，记录翻车原因 |
| 多条不过且同类（如全缺出处） | 是，但根因在提示词 | 打回 + 修提示词（进提示词库更新） |
| 产出物类型不对（要清单给了报告） | 不是打回 | 回步骤①——目标描述不清，重定目标 |
| 质量够但方向偏（做对了错的事） | 不是打回 | 回步骤①/②——目标或步骤拆错了，打回只会做出更精致的错 |
| 第 2 轮同类错误仍不过 | 停 | 升级：换方法/换工具/人自己做，记录为"AI 当前边界" |

**关键区分**：打回解决"做得不对"，回①②解决"做错了事"。用打回解决方向问题 = 第 3 轮成本失控。

## 四、三件资产模板与月度盘点

### 提示词库

```markdown
# 提示词：<任务类型>（如 周报初稿）
版本：v3（2026-10-02 更新）
提示词正文：
  <指令，含目标/约束/验收标准的插槽>
验证记录：
  2026-09-12 首验通过（3/3 验收条）
  2026-09-20 用 2 次，1 次打回（原因：数据段缺出处 → v2 加出处要求）
  2026-10-02 用 3 次，0 打回（v3 稳定）
状态：稳定 / 观察中（<2 次验证的不算验证过，标"观察中"）
```

**入库判据**：≥2 次验证、0 或可解释的打回 → 入库；没验证过的提示词 = 草稿，不进库（"感觉好用"不是验证）。

### 翻车记录

```markdown
# 翻车：<日期> <任务类型>
现象：<AI 做错了什么，具体>
根因：<定位到的原因；没定位到写"未定位">
我怎么纠的：<纠正动作>
是否进验收清单：<是（已补第__条）/ 否（原因：偶发/太特化）>
出现次数：<同类第几次>（≥3 次强制进验收清单）
```

**价值**：翻车记录是"你不可被替代的经验点"的原始形态——AI 翻过的车你记得住、能提前拦，它下次还翻。三个月的翻车记录 = 一个领域里"知道哪里会错"的地图，这个东西买不到、抄不走。

### 月度盘点（15 分钟，每月一次）

```
提示词库：新增 __ 条 / 观察中转正 __ 条 / 失效退役 __ 条（失效原因记录）
验收清单：新增条款 __ 条（来自 __ 次返工/翻车）/ 审查下线 __ 条（拦截 0 次的）
翻车记录：本月 __ 条 / 重复 ≥3 次已转清单 __ 条 / 高频翻车类型 Top1：__
结论：下月重点（修哪类提示词 / 补哪类清单 / 哪类任务 AI 边界明确，考虑换方案）
```

## 五、"用熟了 = 智能体开发能力"的对照

| 个人 AI 教练闭环 | 智能体开发员的岗位动作 |
|---|---|
| 写目标+验收标准 | 定义 Agent 的任务规格与成功判据 |
| AI 拆步骤 | 任务规划（planner） |
| 分步下指令+逐步验收 | 工具调用编排（每步产出物校验） |
| 打回机制（2 轮上限） | 失败重试与回退策略 |
| 提示词库 | 指令/系统提示模板管理 |
| 验收清单 | 输出校验器（validator） |
| 翻车记录 | 错误日志与边界案例库 |

**含义**：你不需要"转行"去当智能体开发员——把个人闭环用熟（三个月），你就在用自己的工作流复现这个岗位的完整动作集。这是"能力迁移"最具体的路径：不是学岗位的名字，是跑岗位的动作。
